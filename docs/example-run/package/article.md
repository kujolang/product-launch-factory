# A Visible Path from Website Finding to Checked Repair

Small web teams often need to repair a site without losing sight of what changed or surrendering control of what goes live. WebOps Factory is designed to give reviewers a visible path from a supported finding to a checked repair candidate, with the evidence needed to assess the result before deciding what happens next. [copied-site-repair-and-review-workflow, reviewable-run-outputs]

The repository describes a workflow that copies a static website, inspects the copy, asks specialist agents for repairs, applies only allowed edits, checks the result again and sends the exact patch to an independent model reviewer. The original site is not edited, and the process stops at human review rather than approving or deploying the candidate. [copied-site-repair-and-review-workflow]

That process is visible on a factory floor showing handoffs, proposed repair values, reasons, browser screenshots, verification reports and statuses drawn from retained run records. Reviewers can inspect the imported bytes, repaired candidate, before-and-after findings, specialist and independent-review responses, exact repair diff, SiteProbe and Lens artifacts, and a package that binds the candidate and evidence to file hashes. Those records support inspection; they do not prove that a change is correct or ready for release. [visible-floor-retained-records, reviewable-run-outputs]

The current release is deliberately focused. It supports four repair categories: missing or empty page titles, missing or empty search descriptions, images without alt attributes, and broken internal file links. Agents cannot introduce commands, executable files, arbitrary HTML, external repair targets or new repair operations. Failed checks or requested revisions leave the run blocked with its evidence instead of producing an approval package. [supported-repair-types, controller-input-and-failure-boundaries]

One recorded live example offers a concrete illustration, not a performance promise. The verification record reports that the run repaired five supported findings across three pages in 43.443 seconds using three specialist calls and one independent review. SiteProbe verification passed before and after the repairs, Lens passed its final homepage desktop and mobile checks, and the independent reviewer returned “pass.” The run still ended in approval_required, not deployment, and findings outside the four supported repair types remained visible. [recorded-live-example-result, recorded-example-check-results]

The boundaries matter. WebOps Factory accepts bounded static exports, not framework projects or server applications. Its checks do not establish perfect SEO, accessibility conformance or security certification, and they do not cover fragment-only links, external link health, rankings or analytics. Browser checks cover the homepage at desktop and mobile sizes, while the static audit examines imported HTML pages. Human review and deployment remain separate. Recorded timings came from specific conditions and should not be treated as onboarding estimates, benchmarks or guarantees. [static-export-intake-boundaries, coverage-and-exclusions, timing-scope-and-exclusions, verification-commands-and-human-review]

For a small team or agency, the practical result is a focused candidate that can be examined before entering the team’s own release process.
